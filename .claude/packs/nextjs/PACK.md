# PACK: Next.js (App Router)

Agency conventions for Next.js 14+ projects. This file is the pack's source of conventions — universal agents must read it before any task in a project whose ABOUT.md declares `Active pack: nextjs`. The `nextjs-specialist` agent resides in `.claude/agents/` and activates when ABOUT.md points to this pack. Wherever the project's ABOUT.md diverges from this pack, ABOUT.md wins.

## Non-negotiable rules

- **App Router always.** Pages Router only for legacy maintenance, never in new code. Never mix `app/` and `pages/` for new routes.
- **Strict TypeScript.** `strict: true` in tsconfig, no explicit `any` without a justifying comment. Prefer `unknown` + narrowing.
- **Server Components by default.** `"use client"` only on the interactive leaf (button, form, component with state/effects). Never on the root layout, never on a whole page "for convenience".
- **`next/image` and `next/font` are mandatory.** Never a raw `<img>`, never an external font `<link>` in the `<head>` (causes CLS and blocks render).
- **Server-side validation always.** Every Server Action and route handler validates input with Zod before touching any logic. The client is never trusted.

## Folder structure

```
app/                    # routes, layouts, route handlers
  (marketing)/          # route group: public pages (does not affect the URL)
  (app)/                # route group: logged-in area
  api/*/route.ts        # route handlers (only when an external client consumes it; otherwise, Server Action)
  layout.tsx            # root: html/body, fonts, minimal providers
  sitemap.ts robots.ts  # generated by code, never stale static files
components/
  ui/                   # reusable primitives (Button, Card...)
  <domain>/             # components by domain (checkout/, blog/...)
lib/
  actions/              # Server Actions ("use server" at the top of the file)
  validations/          # Zod schemas (single source of truth for types: z.infer)
  db.ts, utils.ts       # data access and helpers
```

- Every route segment with dynamic data has `loading.tsx` (or `<Suspense>`) and `error.tsx`. No exceptions on public routes.
- `not-found.tsx` at the root of `app/` customized with the client's identity.
- Colocation: a component used by a single route may live inside the segment (`app/(marketing)/pricing/_components/`). Used by 2+ routes → `components/`.

## Rendering and data fetching

- **Decide the strategy per route, never one global default.** Landing/institutional → static (build). Content that changes (blog, catalog) → ISR with explicit `revalidate`. Per-user data (dashboard, cart) → dynamic + streaming with `<Suspense>`.
- Every `fetch` declares its cache explicitly: `{ next: { revalidate: N, tags: ['x'] } }` or `cache: 'no-store'`. Leaving the implicit default is forbidden — the behavior changed between Next versions and becomes a silent bug.
- Independent fetches in parallel (`Promise.all`); sequential only when one depends on the other's result. A serial `await` waterfall is a performance bug, not a style choice.
- Data flows down via Server Component props. **Anti-pattern:** fetching in a client component (useEffect/SWR) data that the parent Server Component could fetch. SWR/React Query only for data that changes through interaction (filtered search, polling), never for the first render.

## Mutations: Server Actions

- Every mutation goes through a Server Action, not a route handler (route handlers only for webhooks/APIs consumed by third parties).
- Mandatory action structure:
  1. Validate input with a Zod schema (`safeParse`).
  2. Check authentication/authorization **inside the action** (actions are public endpoints — middleware does not protect them).
  3. Execute the mutation; return a typed error (`{ ok: false, error }`), never `throw` for an expected error.
  4. `revalidatePath`/`revalidateTag` for whatever the mutation affected. A short global cache to "compensate" for a mutation without revalidation is an anti-pattern.
- Client feedback: `useActionState` for form errors; `useOptimistic` when the UX calls for an immediate response.

## SEO (mandatory in every project — clients pay for this)

- Metadata API on **every** public page: `title` (template in the layout: `%s | Client Name`), `description`, `alternates.canonical`, Open Graph with a 1200x630 image.
- `generateMetadata` on dynamic routes — data from the entity itself, never generic repeated metadata.
- `sitemap.ts` and `robots.ts` generated by code. Structured data (JSON-LD) for local business, product and article where applicable.
- `lang` on the root layout's `<html>` set to the project language (line 4 of ABOUT.md — e.g. `en`, `pt-BR`).

## Performance (acceptance criteria)

- LCP < 2.5s, CLS < 0.1, INP < 200ms on simulated 4G (Lighthouse mobile ≥ 90 for performance on landing pages).
- LCP image with `priority`; the rest lazy (the `next/image` default). Always a correct `sizes` on responsive images.
- Fonts via `next/font` with `display: 'swap'`; at most 2 families.
- Analyze the bundle before delivering (`@next/bundle-analyzer`); a heavy library in a client component requires justification or `next/dynamic`.
- Middleware only for auth/redirect/geo — it runs at the edge, no heavy logic or database calls.

## Anti-patterns (reject in code review)

| Anti-pattern | Fix |
|---|---|
| `useEffect` + `fetch` for first-render data | Fetch in the Server Component and pass via props |
| `"use client"` on the root layout or a whole page | Isolate interactivity in the leaf; the page stays server |
| Context provider wrapping the whole tree for one widget | Provider on the smallest possible subtree |
| `<img>`, `<link href="fonts.googleapis...">` | `next/image`, `next/font` |
| Server Action without an auth check ("middleware already protects it") | Auth inside the action, always |
| Secret (`process.env.X`) referenced in a client component | Only `NEXT_PUBLIC_*` on the client; secrets stay on the server |
| `fetch` without declared cache | Explicit `revalidate`/`tags`/`no-store` |
| Route handler for an internal mutation of the app itself | Server Action |
| Short global cache instead of post-mutation `revalidateTag` | Revalidation driven by tag/path |
| TS enum in new code | Union of literals or `as const` |

## Deploy checklist (Vercel)

- [ ] Local `next build` with no errors or type warnings; `tsc --noEmit` clean
- [ ] Env vars registered on Vercel (Production + Preview) and validated at boot (fail fast if missing); no secret with the `NEXT_PUBLIC_` prefix
- [ ] Domain + `www` configured with a canonical redirect (only one wins); page canonicals match the final domain
- [ ] `sitemap.xml` and `robots.txt` respond 200 in production; robots does NOT block production (and blocks previews, which Vercel already protects with noindex)
- [ ] OG image renders in a validator (opengraph.xyz) or in a real share test on the channels the client's audience actually uses (market specifics live in the locale file, `.claude/locales/<language>.md`)
- [ ] Custom 404; error routes tested (force an error and see `error.tsx`)
- [ ] Lighthouse in production (not on preview): performance ≥ 90 mobile on key pages
- [ ] Forms tested end to end in production (real submission, email arrives, validation error shows)
- [ ] Client analytics/tag installed via `@next/third-parties` or a script with the proper `strategy`
- [ ] Redirects from the old site's URLs mapped in `next.config.js` (migrate without losing SEO)
